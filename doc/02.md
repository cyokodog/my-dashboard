# リアクティビティの比較：Svelte vs Vue3 vs React

フロントエンドフレームワークにおける「状態管理」と「リアクティビティ」の実装方法には大きな違いがあります。本ドキュメントでは、Svelte、Vue3、React の 3 つを比較し、それぞれのアプローチの透明性と合理性について考察します。

---

## Svelte ストアの自動購読（`$`プレフィックス）

Svelte には「魔法」と呼ばれる暗黙的な仕組みがあります。その代表が**`$`プレフィックスによるストアの自動購読**です。

### 基本的な仕組み

```typescript
const todosCtx = useTodos();

// $todosCtx で直接ストアの中身を取得
console.log($todosCtx.inputText); // TodoState.inputText にアクセス
console.log($todosCtx.sections); // TodoState.sections にアクセス
```

#### なぜ動くのか？

`useTodos()`の返り値を見ると：

```typescript
// src/lib/useTodos.ts
export const useTodos = () => {
  const { subscribe, set, update } = writable<TodoState>(initialState);

  return {
    subscribe, // ← これが重要！
    loadFromStorage,
    updateSections: (sections) => {
      /* ... */
    },
    updateInputText: (inputText) => {
      /* ... */
    },
    toggleEditing: () => {
      /* ... */
    },
  };
};
```

**`subscribe`メソッドを返すオブジェクト = Svelte ストア**として認識されます。

#### `$`プレフィックスの動作

```typescript
const todosCtx = useTodos();
// → { subscribe, loadFromStorage, updateSections, ... }

let todoState = $derived($todosCtx);
//                       ^^^^^^^^
//                       ↓
//                       todosCtx.subscribe(value => {
//                         return value;  // TodoState オブジェクト
//                       })
```

`$todosCtx`は以下を自動的に行います：

1. **`todosCtx.subscribe()`を呼び出す**
2. **ストアの現在値を取得**（`TodoState`型のオブジェクト）
3. **値が変わったら自動的に再レンダリング**

つまり、`$todosCtx`の結果は：

```typescript
{
  sections: [],
  inputText: '',
  isEditing: false,
  updatedAt: 1234567890
}
```

だから、`todoState.inputText`や`todoState.sections`にアクセスできます。

### 明示的な書き方（魔法なし）

本来は以下のように書くのが「分かりやすい」：

```typescript
import { onMount, onDestroy } from 'svelte';

const todosCtx = useTodos();
let todoState = $state<TodoState>({
  sections: [],
  inputText: '',
  isEditing: false,
  updatedAt: 0,
});

onMount(() => {
  // ストアを購読
  const unsubscribe = todosCtx.subscribe((value) => {
    todoState = value; // 値が変わるたびに更新
  });

  // コンポーネント破棄時に購読解除
  onDestroy(() => {
    unsubscribe();
  });
});

// 使用
console.log(todoState.inputText); // 明示的
```

**何が起きているか完全に明確**ですが、毎回このコードを書くのは面倒です。

### 魔法を使った書き方（Svelte の推奨）

```typescript
const todosCtx = useTodos();

// $todosCtx で直接アクセス
console.log($todosCtx.inputText); // 自動購読 + 自動購読解除
```

- **購読処理が自動化**
- **購読解除も自動化**（コンポーネント破棄時）
- **コード量が大幅に削減**

### `$derived` とは？（Vue の `computed` と同じ）

`$derived` は、**他の値から計算される派生値**を定義するための機能です：

```typescript
const todosCtx = useTodos();

// ✅ 意味がある使い方（派生値の計算）
let itemCount = $derived($todosCtx.sections.length);
let hasItems = $derived($todosCtx.sections.length > 0);
let summary = $derived({
  total: $todosCtx.sections.length,
  checked: $todosCtx.sections.filter((s) => s.checked).length,
});

// ❌ 無意味な使い方（単なるコピー）
let todoState = $derived($todosCtx); // これは不要
```

**Vue の `computed` と同じ**で、元の値が変わったら自動的に再計算されます：

```typescript
// Vue の computed と同じ
import { computed } from 'vue';
let itemCount = computed(() => state.sections.length); // Vue
let itemCount = $derived($todosCtx.sections.length); // Svelte
```

### イベントハンドラでのパフォーマンス最適化

#### 問題：関数内での複数回アクセス

イベントハンドラ内で`$store`を使うと、**毎回 subscribe/unsubscribe が実行されます**：

```typescript
// ❌ 非効率（3回subscribe/unsubscribe）
const toggleTodoEdit = () => {
  if ($todosCtx.isEditing) {
    // 1回目
    const newSections = parseTodos($todosCtx.inputText); // 2回目
    todosCtx.updateSections(newSections);
  } else {
    const text = sectionsToText($todosCtx.sections); // 3回目
    todosCtx.updateInputText(text);
  }
  todosCtx.toggleEditing();
};
```

Svelte のコンパイラは`$todosCtx`を以下のように変換します：

```typescript
// コンパイル後のイメージ（簡略化）
function get_store_value(store) {
  let value;
  const unsubscribe = store.subscribe((v) => (value = v));
  unsubscribe(); // 即座にunsubscribe
  return value;
}
```

つまり、**`$store`を使うたびに subscribe/unsubscribe のペアが実行される**ため、複数回アクセスすると非効率です。

#### 解決策：関数の最初で 1 回だけ取得

```typescript
// ✅ 効率的（1回のみsubscribe/unsubscribe）
const toggleTodoEdit = () => {
  const state = $todosCtx; // 1回だけアクセス
  if (state.isEditing) {
    const newSections = parseTodos(state.inputText);
    todosCtx.updateSections(newSections);
  } else {
    const text = sectionsToText(state.sections);
    todosCtx.updateInputText(text);
  }
  todosCtx.toggleEditing();
};
```

**関数の最初で 1 回だけ`$store`にアクセス**し、その値を変数に保存します。以降はその変数を使います。

#### 代替案：リアクティブな値として保持

もしテンプレートでも同じ値を使う場合は、トップレベルでリアクティブに保持する方法もあります：

```typescript
// トップレベルでリアクティブに保持
let state = $derived($todosCtx);

const toggleTodoEdit = () => {
  // subscribe不要、state はすでに最新の値を持っている
  if (state.isEditing) {
    const newSections = parseTodos(state.inputText);
    todosCtx.updateSections(newSections);
  }
  todosCtx.toggleEditing();
};
```

ただし、この方法は：

- **常にリアクティブに監視される**（メモリコスト）
- テンプレートでも値を使う場合は有効
- イベントハンドラだけで使う場合は過剰

#### ベストプラクティス

| 用途                           | 推奨方法                                | 理由                           |
| ------------------------------ | --------------------------------------- | ------------------------------ |
| **イベントハンドラのみで使用** | 関数内で`const state = $store`          | 必要な時だけ subscribe         |
| **テンプレートでも使用**       | トップレベルで`let state = $derived`    | リアクティブに監視、再利用可能 |
| **複数プロパティにアクセス**   | 関数内で 1 回だけ`const state = $store` | subscribe 回数を最小限に抑える |

**結論：イベントハンドラ内では、関数の最初で 1 回だけ`$store`にアクセスし、その値を変数に保存する**のがベストプラクティスです。

### Svelte の評価

| 項目         | メリット                  | デメリット                        |
| ------------ | ------------------------- | --------------------------------- |
| **コード量** | ✅ 大幅に削減される       | ❌ ボイラープレートが隠蔽される   |
| **可読性**   | ✅ シンプルに見える       | ❌ 何が起きているか分かりにくい   |
| **デバッグ** | ❌ 問題の原因が追いづらい | ❌ 「いつ更新されたか」が不明確   |
| **学習曲線** | ✅ 初心者でも書ける       | ❌ 仕組みを理解しないまま使いがち |
| **保守性**   | ✅ 統一されたパターン     | ❌ フレームワーク依存が強い       |
| **透明性**   | ❌ コンパイラマジック     | ❌ ランタイムの挙動が見えない     |

## Vue3 の Proxy ベースリアクティビティ

Vue3 は JavaScript の**Proxy API**を使ってリアクティビティを実現しています。これは**透明性が高く、仕組みが想像しやすい**設計です。

### 基本的な使い方

```typescript
import { reactive, computed } from 'vue';

// 明示的に reactive() で包む
const state = reactive({
  inputText: '',
  isEditing: false,
  sections: [],
});

// 明示的に computed() で派生値を定義
const hasItems = computed(() => state.sections.length > 0);

// 通常の代入で更新される
const toggleEdit = () => {
  state.isEditing = !state.isEditing;
};
```

### Proxy の仕組み（透明性）

Vue3 の `reactive()` は、内部的に以下のような Proxy を作成します：

```typescript
// Vue3 の reactive() の実体（簡略化）
function reactive<T extends object>(target: T): T {
  return new Proxy(target, {
    get(target, key) {
      track(target, key); // 依存関係を追跡
      return Reflect.get(target, key);
    },
    set(target, key, value) {
      const result = Reflect.set(target, key, value);
      trigger(target, key); // 変更を通知
      return result;
    },
  });
}
```

**Proxy を知っていれば、動作が手に取るように分かる**。これが Vue3 の大きな利点です。

### TSX との組み合わせ

Vue3 は TSX（TypeScript + JSX）と相性が良く、テンプレート構文を使わずに純粋な TypeScript で書けます：

```tsx
import { defineComponent, reactive, computed } from 'vue';

export default defineComponent({
  setup() {
    const state = reactive({
      inputText: '',
      isEditing: false,
      sections: [],
    });

    const toggleEdit = () => {
      state.isEditing = !state.isEditing;
    };

    return () => (
      <div>
        <input v-model={state.inputText} />
        <button onClick={toggleEdit}>
          {state.isEditing ? '確定' : '編集'}
        </button>
        {state.sections.map((section) => (
          <div key={section.id}>{section.text}</div>
        ))}
      </div>
    );
  },
});
```

**テンプレート構文を学ぶ必要がなく、TypeScript の型推論がフルに効く**。

### ネストしたオブジェクトの扱い（React との比較）

Vue3 の Proxy ベースは、**ネストしたオブジェクトの更新が非常に合理的**です：

```typescript
const state = reactive({
  user: {
    profile: {
      name: 'John',
      age: 30,
    },
  },
});

// これだけで OK（Proxy が自動的にネストを追跡）
state.user.profile.name = 'Jane';
```

Proxy は**再帰的に適用される**ため、どんなに深い階層でも追跡できます。

### Vue3 の評価

| 項目         | 評価                                      |
| ------------ | ----------------------------------------- |
| **コード量** | ⭐⭐⭐⭐ 適度に簡潔                       |
| **可読性**   | ⭐⭐⭐⭐⭐ Proxy を知っていれば透明       |
| **デバッグ** | ⭐⭐⭐⭐ ブレークポイントが置きやすい     |
| **学習曲線** | ⭐⭐⭐⭐ Proxy の知識があればスムーズ     |
| **保守性**   | ⭐⭐⭐⭐⭐ TypeScript との親和性が高い    |
| **透明性**   | ⭐⭐⭐⭐⭐ 仕組みが想像できる             |
| **TSX 対応** | ⭐⭐⭐⭐⭐ テンプレート構文不要           |
| **ネスト**   | ⭐⭐⭐⭐⭐ Proxy が自動的に深い階層も追跡 |

## React の Immutable アプローチ

React は**状態の不変性（Immutability）**を前提とした設計です。状態を更新する際は、常に**新しいオブジェクトを作成**します。

### 基本的な使い方

```tsx
import { useState } from 'react';

const [state, setState] = useState({
  inputText: '',
  isEditing: false,
  sections: [],
});

// 明示的に新しいオブジェクトを作成
const toggleEdit = () => {
  setState({ ...state, isEditing: !state.isEditing });
};
```

### ネストしたオブジェクトの問題

React の最大の問題点は、**ネストしたオブジェクトを更新する際のコード量**です：

```tsx
const [state, setState] = useState({
  user: {
    profile: {
      name: 'John',
      age: 30,
    },
  },
});

// name だけ変更したいのに、全体をコピーする必要がある
setState({
  ...state,
  user: {
    ...state.user,
    profile: {
      ...state.user.profile,
      name: 'Jane',
    },
  },
});
```

**たった 1 つのプロパティを変更するのに、3 階層すべてをスプレッド構文でコピー**する必要があります。

### なぜこんな設計なのか？

React は**参照の変化**で再レンダリングを判断します：

```tsx
// これは再レンダリングされない（参照が同じ）
state.user.profile.name = 'Jane';
setState(state); // ❌ 参照が変わっていない

// これは再レンダリングされる（参照が変わる）
setState({ ...state }); // ✅ 新しいオブジェクト
```

この設計により：

- **変更検知が高速**（参照比較のみ）
- **タイムトラベルデバッグが可能**（過去の状態を保持）
- **関数型プログラミングの思想**（純粋性を重視）

しかし、**実用性を犠牲にしている**と言えます。

### Immer による改善

React コミュニティでは、Immer というライブラリで問題を緩和しています：

```tsx
import { useImmer } from 'use-immer';

const [state, updateState] = useImmer({
  user: {
    profile: {
      name: 'John',
      age: 30,
    },
  },
});

// Immer を使えば、Vue3 のように書ける
updateState((draft) => {
  draft.user.profile.name = 'Jane';
});
```

**Immer は内部で Proxy を使っている**ので、結局「Proxy ベースが優れている」ことの証明です。

### React の評価

| 項目         | 評価                                  |
| ------------ | ------------------------------------- |
| **コード量** | ⭐⭐ ネストが深いと非常に冗長         |
| **可読性**   | ⭐⭐⭐ 明示的だが煩雑                 |
| **デバッグ** | ⭐⭐⭐⭐ タイムトラベルデバッグ可能   |
| **学習曲線** | ⭐⭐⭐ Immutability の理解が必要      |
| **保守性**   | ⭐⭐⭐ ボイラープレートが多い         |
| **透明性**   | ⭐⭐⭐⭐⭐ 非常に明示的               |
| **TSX 対応** | ⭐⭐⭐⭐⭐ JSX が標準                 |
| **ネスト**   | ⭐ **非常に非効率**（全階層をコピー） |

## 結論：Vue3 Proxy ベースの優位性

### なぜ Proxy ベースが優れているのか

1. **透明性が高い**

   - Proxy API を知っていれば、仕組みが手に取るように分かる
   - ブラックボックスがない

2. **ネストしたオブジェクトの扱いが合理的**

   - React のようにすべての階層をコピーする必要がない
   - Proxy が自動的に深い階層も追跡する

3. **TypeScript との親和性**

   - TSX を使えばテンプレート構文が不要
   - 型推論が完璧に効く

4. **デバッグが容易**
   - ブレークポイントを置けば、どこで値が変わったか一目瞭然
   - タイムトラベルデバッグも可能（Vue DevTools）

### React の Immutable アプローチが合理性に欠ける理由

```tsx
// ❌ React: たった1つのプロパティを変更するのに3階層すべてコピー
setState({
  ...state,
  user: {
    ...state.user,
    profile: {
      ...state.user.profile,
      name: 'Jane',
    },
  },
});

// ✅ Vue3: 通常の代入で完結
state.user.profile.name = 'Jane';
```

**React が Immer（内部で Proxy を使用）を使わないと現実的でない**という事実が、Proxy ベースの優位性を証明しています。

### Svelte の「魔法」が避けられるべき理由

- **仕組みが不透明**（コンパイラが何をしているか分からない）
- **デバッグが困難**（ブレークポイントが効かない場合がある）
- **フレームワーク依存が強すぎる**（将来的な移行が困難）

## 本プロジェクトでの採用理由

このプロジェクトで Svelte を選んだのは：

1. **個人開発**であり、透明性よりも生産性を優先
2. **学習教材**として「魔法」を理解する練習
3. **ファイルサイズ小**（Cloudflare Workers に最適）

**もしチームで開発するなら、Vue3 + TSX を選ぶべき**です。理由：

- コードレビューしやすい
- 新人が入っても理解しやすい
- デバッグが容易
- バックエンドエンジニアにも分かりやすい

## 参考：各フレームワークの思想

| フレームワーク | 思想                             | 対象                           |
| -------------- | -------------------------------- | ------------------------------ |
| **Svelte**     | 「コンパイラが全部やる」         | 初心者・個人開発               |
| **Vue3**       | 「透明性と生産性のバランス」     | バックエンド出身者             |
| **React**      | 「関数型・不変性・明示性を重視」 | 大規模チーム・エンタープライズ |

どれが「正しい」わけではなく、**プロジェクトの性質と開発者の好みで選ぶべき**です。

ただし、**「仕組みを理解した上で使う」** ことは、どのフレームワークでも重要です。
